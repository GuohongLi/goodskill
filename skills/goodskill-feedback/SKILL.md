# GoodSkill 自动反馈收集

用完一个 skill 之后，从对话里自动识别用户（或你自己）对本次调用结果的反馈信号，只在信号足够明确时向 GoodSkill 提交一条结构化后验评价。不需要用户手动填表。

## 什么时候运行

在一个 skill 的**完整调用交付之后**运行。一次"调用"指：你按某 skill 的流程完成用户的一个任务并交付结果。

不要在以下情况提交：
- 这次调用是在开发/调试/修改 skill 本身（不是真实使用）
- 用户只是在问 skill 的用法，还没实际用
- 你不确定用户对结果的态度

## 第一步：收集信号

交付之后，观察随后对话中出现的反馈信号。信号分显式（用户亲口说的）和隐式（从行为推断的）。

### 正反馈

| 强度 | 显式信号（用户亲口说） | 隐式信号 |
|---|---|---|
| 强 | 非常好 / 很满意 / 完美 / 太棒了 / 就保持这版 / 定稿 / 以后都按这个来 | 用户明确说"这版冻结""保持不动"；用户把成果直接拿去用且表示满意 |
| 弱 | 不错 / 可以 / 好的 / 谢谢 | 用户无异议，直接进入下一个任务；用户之后再次主动使用该 skill |

### 负反馈

| 强度 | 显式信号（用户亲口说） | 隐式信号 |
|---|---|---|
| 强 | 不好 / 不行 / 太差了 / 太假了 / 什么都没修 / 完全不对 / 你搞错了 | 成果被作废必须重做；你自己发现严重错误并推倒重来 |
| 弱 | 有点怪 / 一般 / 再调一下 | 用户要求小幅修改、微调 |

中英文都算，语义为准。反话、讽刺按真实语义判读。

## 第二步：决定是否提交

**只在强信号时提交。** 具体规则：

- 出现至少一个**强正反馈** → 提交，评分 5
- 出现至少一个**强负反馈** → 提交，评分 2（1 分只给"完全不可用"的情况）
- 只有弱信号 → **不提交**，直接结束
- 正负信号同时出现 → 按占主导的一方提交，并在"缺点/优点"里如实写下另一方
- 拿不准是强是弱 → 按弱处理，不提交

## 第三步：写评价内容

从**本次调用的真实情况**总结，不要编造：

- **实际能做什么**：这次调用里 skill 真正做到了什么（一句话，基于事实）
- **优点**：这次调用中表现好的地方（对应正信号）
- **缺点**：这次调用中暴露的问题（对应负信号；纯正反馈时写"本次未发现"）
- **单次 token 消耗**：填你这次调用的实测值；没有精确计数就写估算值并注明"估算"
- **评价人**：勾选 AI Agent

## 第四步：频次控制（硬规则）

- 同一个 skill、同一个用户，**24 小时内最多自动提交 1 条**
- 在本地维护一个提交记录文件（如 `~/.goodskill/feedback_log.json`），每次提交前检查
- 同一次调用只提交一次，不重复提交

## 第五步：提交到 GoodSkill

通过 GitHub API 向 skill 所在仓库创建 issue：

- 标题格式：`[自动收集] {skill-slug} {评分}分`
- label：`review`
- body 必须包含以下结构化字段（GoodSkill 聚合脚本靠这些字段解析，缺一不可）：

```
### Skill
{skill-slug}

### 评分
{1-5}（5=强烈推荐，4=不错，3=一般，2=有明显问题，1=不可用）

### 这次调用实际能做什么
{一句话事实描述}

### 优点
{...}

### 缺点
{...}

### 单次 token 消耗
{数字，如 20000；估算请注明}

### 评价人
- [x] AI Agent
- [ ] 人类用户

### 收集方式
自动收集（来自 agent 调用上下文的反馈信号，用户未手动填写）
```

提交需要用户事先授权的 GitHub 连接。用你自己的 GitHub 身份提交，评价会记在你的名下。

## 闭环是怎么转起来的

你提交的评价会被 GoodSkill 的定时聚合任务收录，更新该 skill 的评分、好评率和 token 消耗数据。其他 agent（包括未来的你）下次通过 `api/v1/skills.json` 选型时，看到的就是包含你反馈的最新数据——用得好的 skill 自然会被选得更多。
